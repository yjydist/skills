# issue 撰写指南

本文说明如何把 session 中的讨论归纳成 issue: 信息来源, 去重合并, 类型判定, 标题与正文写法, 以及何时拆分 sub-issue.

## 信息来源与收集方法

session 中的 issue 素材通常出现在以下位置:

+ 用户明确提出的要求: "记得修一下", "这里以后要支持", "把这个记下来".
+ 讨论中被延后的 bug: 用户指出了问题但当前任务没有处理, 或者修复被移出了本轮范围.
+ 被搁置或简化的方案: 为了先完成任务而绕开的路径, 例如 "先用硬编码顶替", "这块错误处理后面再补".
+ 用户认可的问题描述: 讨论中双方确认存在, 但没有落实到本次改动的内容.

回顾时区分三个层次: 用户明确说过的, 讨论中隐含认可的, 以及自己推测的. 前两层可以进入清单, 第三层必须标注为推测并请用户确认, 不能写成结论.

## 去重与合并

+ 同一问题在 session 中被多次以不同角度提到, 合并为一条, 保留最完整的表述.
+ 同一根因的多个表象合并为一条 issue, 在正文中列出各表象.
+ 合并的判断依据是 "修一次就能全部解决". 修复方式不同的两个表象保持分开.
+ 合并后在正文中注明信息来自 session 中的哪些讨论点, 便于用户核对.

## 类型判定

| 类型 | 判定标准 | 示例 |
| --- | --- | --- |
| fix | 现有行为不符合预期, 有明确的错误表现 | 重试逻辑在超时后仍继续请求 |
| enhancement | 现有功能可用, 但有明确的改进方向 | 配置项缺少校验, 非法值静默通过 |
| idea | 尚无明确问题, 是对下一步的设想 | 支持 导出为 CSV 的可能性 |

边界情况按用户表述倾向归类; 用户没有倾向时, 已发生的问题归 fix, 未发生的设想想归 idea. 类型决定默认标签, 最终以仓库已有标签为准.

## 标题写法

+ 具体到能独立理解, 脱离 session 上下文也能看懂要做什么.
+ 以现象或目标开头, 不以讨论过程开头. 写 "分页参数为 0 时返回全部数据", 不写 "今天讨论的那个分页问题".
+ 不在标题中堆叠多个主题. 一条 issue 一个主题, 拆不下的内容放正文.

## 正文结构

推荐结构:

```markdown
## 背景

<问题或想法来自哪次讨论, 简述当时的上下文.>

## 问题 / 目标

<fix 写当前错误表现和触发条件; enhancement 和 idea 写期望达到的状态.>

## 建议方案

<session 中讨论过的处理思路. 没有讨论过方案时写 "方案待定", 不编造.>
```

信息不足时的处理:

+ 缺触发条件, 期望行为等关键信息的, 在对应小节末尾加一行: `> 待确认: <缺什么>`.
+ 多个信息缺口集中列在正文末尾的 "待确认" 小节也可以, 保持同一条 issue 内风格一致.
+ 标注待确认的条目在草稿展示时要一并提醒用户, 用户当场能补的先补上.

## sub-issue 拆分判定

标准是 "包含多个可独立执行, 可独立验收的工作项", 不是字数或行数阈值.

满足以下任一信号时考虑拆分:

+ 正文罗列了 3 个以上互不依赖的子任务, 且分属不同模块.
+ 不同子项显然会形成不同的 PR, 由不同的人或不同时机处理.
+ 父 issue 描述的是一个方向或目标, 具体做法需要逐项落实.

不满足时保持单条 issue, 用任务清单(`- [ ]`)在正文中表达子项. 拆分后的父 issue 写总体目标和验收标准, 每个子 issue 只承载一个工作项, 在父 issue 正文中说明拆分关系.
