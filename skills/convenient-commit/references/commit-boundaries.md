# 提交边界指南

处理混合改动, 边界难以判断或非交互环境下需要按改动块暂存时使用. 判断拆分是否降低理解成本, 同时保持每条提交的逻辑完整性.

## 拆分与合并判断

| 判断 | 适用情况 | 处理 |
| --- | --- | --- |
| 拆分 | 存在可以分别说明, 验证和审查的独立目的 | 按目的分组, 再按依赖排序 |
| 合并 | 片段没有独立意义, 或必须跨多条差异才能判断同一行为 | 保留完整变化及其必要配套 |
| 保持 | 已是一条连贯的变化, 拆分只增加跳转和解释成本 | 保持当前边界, 不以行数或文件数要求继续拆分 |

审查每条提交时, 以它的父提交为上下文. 后续提交可以依赖已完成的准备工作, 不要求所有提交都能任意交换顺序或单独 `cherry-pick`. 前面的提交必须无需读取未来的修补就能理解和验证.

纯重构或机械变更可以独立解释并验证时, 通常与行为变化分开. 为已有行为补充能够通过的特征测试, 也可以作为后续重构的准备提交. 只服务于当前实现的微小辅助函数或局部调整, 不必强行拆出.

## 五类边界示例

### 1. 修复一个边界条件

修改边界判断, 更新受影响的调用点, 并加入回归测试.

保留一条提交. 实现与测试共同完成这次修复, 不因跨文件而拆开, 也不拆成修改条件与补测试两条相互补缺的提交.

### 2. 先重构, 再增加行为

先提取重复解析逻辑, 保持行为不变且现有测试通过; 再支持新的输入格式并增加测试.

可以分为两条提交. 第一条完成可验证的重构, 第二条依赖它增加行为. 若提取只是新增行为的几行局部实现, 没有独立价值, 则保留在同一条提交.

### 3. 接口与调用方联动

修改接口字段, 同时更新类型, 调用方和相关测试.

通常保留一条提交, 不按服务端, 类型和客户端机械拆分. 若存在各自可验证的向后兼容步骤, 可以先增加兼容支持, 再迁移调用方, 最后移除旧路径. 每一步都需保持完整, 不留下接口断裂的中间状态.

### 4. 新功能夹带全文件格式化

新增缓存功能, 同时重新格式化整个模块.

缓存逻辑与其测试放在一起. 将无关格式化留在工作区, 或在授权范围内单独提交, 保留用户原有改动. 少量直接服务于本次代码的格式调整无需另建提交. 无法可靠分离时重新检查方案, 不通过丢弃内容制造边界.

### 5. 一个较大的功能

先寻找各自成立且可验证的行为增量, 如先支持一种输入, 再扩展另一种输入.

不按定义类型, 添加空实现, 接入调用和补测试机械拆分. 找不到合理的中间状态时, 保留完整变化并说明原因. 独立的配置, 文档或维护改动仍按其目的判断, 不因同属一个大任务就自动合并.

## 非交互环境下按改动块暂存

仅在已获提交或暂存授权, 且确认已有暂存内容的归属后使用. 补丁应用成功只说明能写入暂存区, 不代表提交边界完整或验证通过.

1. 使用 `git diff -- <路径>` 读取相对于当前暂存区的未暂存差异, 同时用 `git diff --cached -- <路径>` 确认已有暂存部分. 从真实差异中选择当前目的需要的改动块, 不凭记忆重写内容.
2. 将选中的补丁写入仓库外的临时文件. 保留文件头, 上下文和正确的改动块行数. 拆分同一改动块时, 确保补丁基于当前暂存区, 且应用后的文件仍有完整意义.
3. 阅读补丁内容, 确认没有夹带无关改动, 再检查并应用同一份补丁. 以下变量应指向实际创建的临时补丁文件, 并按顺序执行, 检查成功后才应用:

```bash
git apply --cached --check -- "$commit_patch"
git apply --cached -- "$commit_patch"
```

4. 用 `git diff --cached -- <路径>` 和 `git diff -- <路径>` 分别核对选中与剩余内容, 再回到主流程检查完整暂存快照. 若暂存区在检查后发生变化, 重新生成并检查补丁.

+ `git apply --cached` 只修改暂存区, 不会同步修改工作区文件. 不要去掉 `--cached` 后重试, 以免改动用户工作区.
+ 检查失败时, 重新核对当前暂存区和补丁上下文, 不用强行应用或丢弃剩余改动来消除错误.
+ 未跟踪文件不出现在普通 `git diff` 中. 整个文件属于当前提交时直接按路径暂存; 确需拆分时, 构造包含 `new file mode`, `--- /dev/null` 和正确目标路径的新文件补丁, 检查内容和文件模式. 不为获取差异而无差别标记全部未跟踪文件.
+ 无关内容已被暂存时, 仅应用选中补丁并不能隔离它. 仍须遵守主流程对已有暂存内容的保护要求, 无法安全隔离时报告阻塞.
