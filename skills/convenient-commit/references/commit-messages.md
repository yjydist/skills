# 提交消息指南

拟定或检查提交消息时使用. 消息帮助后来者理解改动的目的, 结果和必要背景; 具体写法应由实际差异支持.

## 语言和格式

依次采用用户明确要求, 仓库明确规范, 一致的历史惯例. 阅读仓库说明, 提交检查配置及近期完整消息, 同时判断语言, 类型, 范围命名和正文习惯. 本指南的说明和示例使用简体中文, 实际消息的语言遵循上述顺序.

没有明确规范, 且历史不足以形成一致惯例时, 默认使用中文 Conventional Commits:

```text
<类型>(<范围>): <标题>

<有解释价值时补充的正文>

<确有需要的尾注>
```

范围, 正文和尾注均可省略. 遵循仓库的长度限制, 不额外套用统一的 50/72 字符限制. 结构及破坏性变更标记遵循 [Conventional Commits 规范](https://www.conventionalcommits.org/zh-hans/v1.0.0/).

## 类型, 范围和标题

按主要目的选择类型, 不根据触及的文件扩展名机械判断. 下表是常用选择, 仓库可以定义其他类型:

| 类型 | 主要目的 |
| --- | --- |
| `feat` | 新增能力或行为 |
| `fix` | 修复已有行为的缺陷 |
| `refactor` | 保持已有行为的结构调整 |
| `perf` | 改善性能 |
| `test` | 独立补充或调整测试 |
| `docs` | 改善文档说明 |
| `style` | 不改变行为的格式调整 |
| `build` | 调整构建系统或依赖 |
| `ci` | 调整持续集成流程 |
| `chore` | 无法由更具体类型表达的维护工作 |
| `revert` | 撤销已有提交的变化 |

修复及其回归测试通常仍是一条 `fix` 提交. 不为使用多个类型而拆开完整变化, 也不用 `chore` 掩盖难以解释的混合目的.

范围可省略. 使用仓库已有的稳定模块名称, 避免把多个目录或文件名串成范围.

标题以具体动作描述主要对象和结果, 简洁到能够在提交列表中独立理解. 通常不加末尾句号. 避免只写更新, 优化, 修复问题等无法定位变化的描述, 也避免未经证实的性能或可靠性承诺.

| 笼统标题 | 在对应差异支持下的具体标题 |
| --- | --- |
| `chore: 优化代码` | `refactor(parser): 合并重复的日期解析分支` |
| `fix: 修复问题` | `fix(auth): 拒绝已过期的刷新令牌` |
| `docs: 更新文件` | `docs(install): 补充离线安装步骤` |

## 正文和尾注

简单且标题已解释清楚的变化, 只写标题. 当原因, 取舍或影响无法从标题和差异直接理解时, 在空行后补充正文. 根据实际需要解释:

+ 原有行为或限制, 什么触发了问题, 为什么需要修改.
+ 修改前后的行为差异, 所选方案及影响判断的重要取舍.
+ 兼容性影响, 适用范围, 调用方需要的迁移步骤.

正文补充标题没有表达的信息, 不重复文件清单或逐行复述实现. 不强制每次填充相同栏目. 无法从用户说明, 代码或验证结果中确认的原因, 问题编号和效果, 不写成事实. 缺失信息会影响提交边界或正确性判断时, 先澄清.

验证结果通常放在最终报告. 仓库要求或结果对理解变化有帮助时, 可以写入正文, 但必须与实际执行的检查一致, 不把增加测试写成测试已经通过.

存在破坏性变更时, 使用冒号前的 `!` 或 `BREAKING CHANGE:` 尾注标记, 也可以同时使用. 明确说明不兼容点和必要迁移方式. 问题关联等尾注只引用已经确认的编号和真实关系, 不凭空添加.

## 示例与消息写入

以下示例假定差异确实包含所描述的变化. 仅拟定消息时输出消息文本, 不执行提交命令; 获得提交授权且完成暂存快照验证后, 才使用消息写入示例.

### 简单修改, 只写标题

```text
docs(install): 补充离线安装步骤
```

### 复杂修复, 解释原有问题和行为变化

多行消息使用带引号的 heredoc 配合 `git commit -F -`, 保留真实换行并避免 shell 展开:

```bash
git commit -F - <<'EOF'
fix(auth): 拒绝已过期的刷新令牌

刷新接口原先只检查签名, 已过期但签名有效的令牌仍可换取新令牌.

在签名校验后检查过期时间, 将刚好到期的令牌也视为过期,
并保留原有错误响应格式. 补充刚好到期和已经过期的回归用例.
EOF
```

使用真实换行, 不把字面量 `\n` 当作换行写入消息. 不把包含反引号或 `$()` 的消息拼入会执行展开的 shell 字符串. 单行消息也可用上述方式写入.

### 破坏性变更, 说明迁移方式

```text
feat(api)!: 改用游标分页

为持续更新的列表提供稳定翻页, 请求参数由 offset 改为 cursor.

BREAKING CHANGE: 分页接口不再接受 offset, 调用方需传入上次响应的 next_cursor 作为 cursor.
```

## 消息检查

在主流程核对暂存快照时检查:

+ 标题是否准确描述这条提交的主要结果, 类型和范围是否符合该结果.
+ 正文是否有必要, 所写原因, 效果和验证声明是否有依据.
+ 兼容性影响是否表达完整, 消息格式和换行是否符合约定.

提交后用主流程中的完整消息检查确认实际写入结果, 包括标题, 正文和尾注. 发现钩子改写消息或实际范围变化时重新核对, 不只检查短标题.
