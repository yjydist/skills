# skill 写作方法

本文件回答"怎样写得好用".

## 1. 描述公式与同级竞争测试

`name` 和 `description` 会进入 skill 列表; 其中 `description` 承担匹配, 是激活前唯一的自然语言匹配依据. 它同时承担两件事: 说明做什么, 说明何时使用.

基本公式:

```text
<做什么, 输出什么>. 在 <用户会说的请求, 对象, 动作或格式> 时使用.
```

写法:

+ 用第三人称陈述, 不写"我可以帮你"或"你可以用这个".
+ 写出用户请求中会出现的具体名词和动词, 不只写领域名.
+ 说明相邻请求的边界, 让不该触发的请求能被排除.
+ 使用与用户一致的语言. 用户混用中英文时保留关键英文术语.
+ 把最关键的触发词放在前面. 部分客户端会压缩或截断描述.

对比例子:

```yaml
# 只有主题, 无法判断何时使用
description: 帮助整理会议内容.

# 有动作, 对象和触发语境
description: 把会议记录整理成纪要, 提取决议和行动项, 分配负责人和截止日期. 在用户贴出会议记录, 提到行动项或需要分配待办时使用.
```

### 同级竞争测试

测试只用 `description`, 不读正文. 客户端在选择 skill 时看不到正文, 正文写得再清楚也不能补救描述.

1. 列出同一仓库或同一安装位置中所有 skill 的 `name` 和 `description`. 竞争范围是本仓库或本安装位置中面向用户的 skill; 外部工具自带的工具型 skill (例如 `.agents/skills` 下的 OpenSpec skill) 默认不参与用户 skill 的触发竞争, 若目标分发环境会加载它们, 则另行测试.
2. 准备一组目标请求, 覆盖不同措辞.
3. 对每条请求, 只根据描述判断哪些 skill 能匹配, 选出最合适的一个.
4. 合格标准: 每条目标请求只定位到本 skill; 不该由本 skill 处理的请求不会定位到它.
5. 两个 skill 同时匹配时, 调整职责边界或描述措辞, 直到只有一个匹配.

记录示例:

| 请求 | 可能匹配 | 结论 | 依据 |
| --- | --- | --- | --- |
| 把这次会议的待办整理出来 | 本 skill | 本 skill | 描述包含会议纪要, 行动项, 待办 |
| 给这次改动写提交消息 | 提交 skill | 其他 skill | 本 skill 的描述不含提交或改动 |
| 解释一下什么是行动项 | 无 | 不触发 | 属于模型常识, 描述没有要求解释概念 |

最后一行同时也是负例: 描述不应宽泛到把常识问答也吸进来.

## 2. 触发语料的构成

触发语料用于验证描述是否能稳定定位. 语料不是单元测试, 不需要覆盖所有分支, 但必须覆盖真实的措辞差异.

正例建议取 5-10 条, 覆盖:

+ 明确点名 skill 的请求.
+ 用户日常口语, 不含 skill 名称.
+ 只给关键词或对象名的简短请求.
+ 带完整背景和交付要求的请求.
+ 与目标请求同义但用词不同的请求.

负例建议取 3-5 条, 覆盖:

+ 与目标领域接近, 但应由相邻 skill 处理的请求.
+ 只需模型常识或一次推理的请求.
+ 一次性任务, 不值得激活 skill.
+ 需要另一个工具或另一类交付物的请求.

太简单, 不需要 skill 的请求不要作为正例. 它们会让描述显得过宽, 也无法证明 skill 有价值; 它们是有效的负例, 用来排除过宽的描述.

每条语料记录:

| 字段 | 内容 |
| --- | --- |
| 请求 | 用户原话或接近原话的表述 |
| 期望归属 | 本 skill, 其他 skill 或无 |
| 判断依据 | 描述中的哪个词或边界支持这个判断 |
| 实际结果 | 自动判断或人工判断的结果 |

修改描述后重跑整组语料, 不只重跑失败的那条. 只修一个用例容易把描述推向另一个极端, 让其他请求失效.

无法启动独立会话时, 由执行者按描述人工判断, 在结果中标注"人工判断", 不写成已自动验证.

## 3. 正文模式

正文按执行顺序组织, 常见结构:

1. 目的和适用边界.
2. 工作流程, 按步骤编号.
3. 每步需要的输入, 判断条件和失败处理.
4. 交付前检查或操作边界.

写作要求:

+ 每条规则都应能改变执行行为. 只解释来源, 历史或动机的段落删掉.
+ 决策规则留在正文, 因为它们每次激活都要用.
+ 确定且可重复执行的操作放进 `scripts/`, 正文说明何时调用和如何读结果.
+ 只在部分分支需要的细节放进 `references/`, 正文说明读取条件.
+ 不复制参考文件或脚本中的硬约束. 需要时指向唯一来源, 避免两处漂移.
+ 正文说明参考文件的读取条件, 让执行者不需要在参考文件之间继续寻找入口.
+ 参数和分支用表格, 有先后关系的步骤用编号列表, 交付检查用清单.
+ 不写模板化章节. 骨架存在后很少被删除, 容易留下与 skill 无关的段落.

对比例子:

```markdown
# 差: 只解释背景, 不改变执行
PDF 是一种常见的文档格式, 包含文本和图片. 处理 PDF 有很多库,
选择合适的库需要了解它们的历史和差异.

# 好: 直接给出判断和动作
需要抽取文本时使用 pdfplumber. 输出表格时保留原始行列,
合并页面时先确认页面顺序.
```

## 4. 按步骤分配自由度

同一个 skill 中, 不同步骤需要不同的具体程度. 不要所有步骤都用同一种写法.

| 自由度 | 适用步骤 | 写法 | 例子 |
| --- | --- | --- | --- |
| 低 | 结果脆弱, 顺序固定, 容易出错, 成功条件可机械判定 | 给出确切命令, 参数, 判定条件和失败处理 | 生成文件后运行固定校验命令; 编译失败时停止, 不交付部分产物 |
| 中 | 存在首选模式, 允许有限变化 | 给模板或伪代码, 标明可调参数和约束 | 按给定表格结构输出, 列和顺序固定, 内容由输入决定 |
| 高 | 多种做法都有效, 需要根据上下文判断 | 给目标, 约束和理由, 由执行者选择 | 评审文档结构时, 说明要检查的维度, 不规定唯一改法 |

判断顺序:

1. 成功条件能否机械判定? 能, 用低自由度.
2. 是否存在明显的首选模式? 有, 用中自由度.
3. 做法是否随输入, 环境或用户目标变化? 是, 用高自由度.

反例:

+ 对需要根据输入调整的设计任务给出唯一命令, 执行者只能机械照做或违背指令.
+ 对必须按固定顺序执行的迁移步骤只写"小心处理", 每次执行结果都可能不同.
+ 整个 skill 只写原则, 没有可执行的步骤.
+ 整个 skill 只写固定命令, 没有说明何时该换做法.

## 5. 常见失败清单

| 症状 | 判断依据 | 改法 |
| --- | --- | --- |
| 描述只写领域 | 描述里没有动作, 对象或触发语境 | 按描述公式补全, 再用同级竞争测试检查 |
| 触发信息只放在正文 | 描述本身无法定位请求, 需要读正文才知道何时使用 | 把触发条件移到描述, 正文只写执行细节 |
| 正文复制硬约束 | 名称规则, 字段长度或目录表同时出现在正文和参考/脚本中 | 删掉正文副本, 指向唯一来源 |
| 参考文件互相引用 | 从参考文件跳到另一个参考文件才能找到规则 | 参考文件之间不互相链接, 所有引用由 SKILL.md 直接指向一层 |
| 模板残留 | 正文仍有占位符, 待办段或与本 skill 无关的章节 | 删除未使用内容, 只保留会改变行为的规则 |
| 依赖厂商机制 | 正文要求某个客户端专有的工具名, 变量, 元数据或调用方式 | 标注适用范围, 提供标准结构下的替代做法 |
| 正文解释动机 | 段落只说明为什么这样做, 不说明做什么 | 删除或压缩成一句判断条件 |
| 所有步骤同一自由度 | 脆弱步骤没有确切命令, 或灵活步骤被唯一做法锁死 | 按步骤重新分配自由度 |
| 未被引用的文件 | `scripts/` 或 `references/` 中存在 `SKILL.md` 没有直接引用或提到的文件 | 删除, 或在正文说明何时使用 |
| 只修好一个用例 | 修改后只重跑失败的那条语料 | 重跑整组语料, 确认没有退化 |
| 一次性任务做成 skill | 请求不会重复, 或只需模型常识 | 说明不适合新建, 直接完成任务或改用其他形式 |
| 用测试代替运行 | 只运行单元测试, 没有实际执行脚本或走完流程 | 按实际使用方式运行一次, 记录真实结果 |
| 正文过长 | 入口接近或超过建议行数, 细节与决策混在一起 | 把细节移入参考文件或脚本, 保留决策和去向 |
| 交付说明夸大 | 把未执行的检查写成已验证, 或遗漏未验证项 | 分开列出已验证项和未验证项, 附原因 |
