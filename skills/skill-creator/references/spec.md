# Agent Skills 规范

本文件汇总 [Agent Skills 规范](https://agentskills.io/specification) 定义的硬约束, 作为 skill-creator 创建和校验 skill 时的唯一规则来源.

标准只约束目录形状和 `SKILL.md` 的 frontmatter. 正文格式, 脚本语言, 加载时机, 调用方式和分发格式由各客户端自行决定, 不属于标准.

## 目录结构

一个 skill 是一个目录, 至少包含 `SKILL.md`:

```text
skill-name/
|-- SKILL.md          # required: metadata + instructions
|-- scripts/          # optional: executable code
|-- references/       # optional: docs loaded on demand
|-- assets/           # optional: templates, images, data
`-- ...               # additional files or directories
```

+ `SKILL.md` 是入口. 客户端在激活 skill 时读取完整正文.
+ `scripts/`, `references/` 和 `assets/` 是标准推荐的约定目录, 不是必需的.
+ 标准允许目录中出现其他文件或子目录. 它们是否被加载或执行取决于客户端.
+ 目录名必须与 frontmatter 的 `name` 相同 (双方按 NFKC 归一化后比较).

最小 `SKILL.md`:

```markdown
---
name: skill-name
description: 说明这个 skill 做什么, 以及何时使用.
---

# 流程

1. 读取必要输入.
2. 按步骤执行并输出结果.
```

## SKILL.md 格式

`SKILL.md` 由 YAML frontmatter 和其后的 Markdown 正文组成. frontmatter 以单独一行 `---` 开始, 以单独一行 `---` 结束.

### frontmatter 字段

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `name` | 是 | NFKC 归一化后 1-64 字符; 只含 Unicode 小写字母和数字, 以及连字符 `-`; 不以连字符开头或结尾; 不含连续连字符; 与父目录名在 NFKC 归一化后相同. |
| `description` | 是 | 1-1024 字符; 非空; 说明做什么和何时使用. |
| `license` | 否 | 许可证名称, 或指向 skill 目录内许可证文件的引用. |
| `compatibility` | 否 | 1-500 字符; 说明运行环境要求, 如目标产品, 系统包, 网络访问. |
| `metadata` | 否 | 字符串键到字符串值的映射. |
| `allowed-tools` | 否 | 空格分隔的工具名字符串; 实验性字段, 支持程度因客户端而异. |

### name

+ 按官方 `skills-ref` 参考实现, 校验前先去除首尾空白并做 NFKC 归一化; 其后所有检查和长度计数都针对这个结果.
+ 去除首尾空白后必须满足本条下面的 Unicode 小写字母, 数字和连字符规则. 首尾空白只是被忽略, 不是放宽字符集: `name: " pdf-processing "` 归一化后为 `pdf-processing`, 合法; 但 `pdf processing` 去掉首尾空白后中间仍有空格, 仍属非法.
+ 长度 1-64 字符, 按归一化后的字符计数, 不按字节.
+ 只允许 Unicode 小写字母和数字, 以及连字符 `-`. 例如 `a-z`, `é`, `技能` 都合法; 采用兼容字符时以 NFKC 归一化后的结果判断.
+ 必须全部为小写, 不能含大写字母.
+ 不能以连字符开头或结尾.
+ 不能出现连续连字符.
+ 必须与父目录名在 NFKC 归一化后完全一致. 这样同一名称的 NFC 与 NFD 写法可以匹配同一目录. 父目录名只做 NFKC 归一化, 不执行 `name` 字段的去除首尾空白步骤, 因此目录名带首尾空白时视为不一致. 校验时使用解析后的实际目录名: 通过符号链接调用时, 比较目标是链接指向的目录名, 而不是链接名.

合法示例:

```yaml
name: pdf-processing
name: data-analysis
name: 技能
name: café
```

非法示例:

```yaml
name: PDF-Processing   # 含大写字母
name: -pdf             # 以连字符开头
name: pdf--processing  # 含连续连字符
name: pdf_processing   # 含下划线
name: 技能!            # 含非字母数字字符
```

### description

+ 长度 1-1024 字符, 不能为空.
+ 说明 skill 做什么, 以及何时使用.
+ 建议包含能帮助客户端识别相关任务的用户用语, 对象名, 动作和格式.
+ 描述会进入客户端的 skill 列表, 是激活前唯一的匹配依据.

合格示例:

```yaml
description: 从 PDF 提取文本和表格, 填写表单并合并文档. 在用户处理 PDF, 提到表单或要求文档抽取时使用.
```

不合格示例:

```yaml
description: 帮助处理 PDF.
```

不合格示例只有领域, 没有具体动作和触发语境.

### license

+ 可选.
+ 写许可证名称, 或指向 skill 目录内的许可证文件.
+ 标准没有规定长度和固定取值.
+ 建议保持简短.

示例:

```yaml
license: Apache-2.0
```

### compatibility

+ 可选.
+ 提供时长度 1-500 字符.
+ 说明目标产品, 需要的系统包, 网络访问或其他环境前提.
+ 大多数 skill 不需要此字段.

示例:

```yaml
compatibility: 需要 Python 3.9+ 和 git.
```

### metadata

+ 可选.
+ 必须是映射, 键和值都是字符串.
+ 标准允许客户端用此字段存放额外属性.
+ 键名建议保持唯一, 避免与其他 skill 或客户端冲突.
+ 未加引号的数字和布尔值会被 YAML 解析为非字符串, 必要时加引号.

示例:

```yaml
metadata:
  author: example-org
  version: "1.0"
```

### allowed-tools

+ 可选.
+ 必须是空格分隔的字符串, 不是列表.
+ 表示 skill 可以预先获准使用的工具.
+ 这是实验性字段, 不同客户端的支持程度不同; 不能假设所有客户端都会执行该声明.

示例:

```yaml
allowed-tools: Bash(git:*) Read
```

### 非标准字段

标准没有定义上述六个字段之外的 frontmatter 字段. 客户端可能忽略不认识的字段, 也可能自行解释. 因此:

+ 非标准字段不能作为 skill 正确运行的前提.
+ 依赖非标准字段时, 必须标注适用的客户端, 并提供不依赖该字段的替代做法.
+ `scripts/validate_skill.py` 把非标准字段列为警告, 严格模式下视为错误.

### 正文

+ frontmatter 之后是 Markdown 正文, 标准不限制正文格式.
+ 客户端激活 skill 时会加载完整正文.

## 渐进披露

标准建议按三层组织内容:

1. metadata: `name` 和 `description`, 启动时加载, 约 100 token.
2. instructions: `SKILL.md` 正文, 激活时加载, 建议少于 5000 token.
3. resources: `scripts/`, `references/` 和 `assets/` 中的文件, 按需加载.

`SKILL.md` 正文建议保持在 500 行以内. 超过时把细节移入参考文件或脚本.

## 文件引用

Agent Skills 规范推荐的写法是相对 skill 根目录的路径. `scripts/validate_skill.py` 的引用检查以此为主: 先按 skill 根目录解析, 找不到再按链接所在文件目录解析.

这个回退是校验器的兼容行为, 不是标准要求: 按标准写的 skill 应只使用相对 skill 根目录的路径, 换成其他客户端时才能解析到同一目标. 两种写法都能通过本 skill 的校验器, 但只能按所在文件目录解析的链接会得到警告, 提示改为相对 skill 根目录. 绝对路径链接 (`/...`) 的目标必须真实存在: 目标不存在按本地链接目标不存在报错, 目标存在时才给可移植性警告. 解析后落在 skill 目录外的链接同样能通过校验, 但会得到可移植性警告.

+ 在 `SKILL.md` 中引用时, 使用相对 skill 根目录的路径, 例如 `references/REFERENCE.md` 或 `scripts/extract.py`. `SKILL.md` 位于根目录, 相对所在文件和相对 skill 根目录在它上面指向同一位置.
+ 在 `references/` 内的文件互相链接时, 标准写法仍是相对 skill 根目录: 链接同目录的 `b.md` 写 `references/b.md`, 链接 `scripts/extract.py` 写 `scripts/extract.py`. 相对所在文件目录的写法 (`b.md`, `../scripts/extract.py`) 只有本 skill 的校验器接受, 换客户端可能失效, 并且会触发警告.
+ 不要使用以 `/` 开头的绝对路径链接, 不要使用 Windows 盘符或 UNC 路径 (如 `C:\work\demo.md`, `\\server\share\demo.md`), 也不要链接到 skill 目录外的文件: 它们在分发后无法解析到同一目标. 绝对路径链接的目标不存在时校验器直接报错 (按本地链接目标不存在处理), 目标存在时给可移植性警告; Windows 盘符或 UNC 路径一律给可移植性警告; 目录外链接给可移植性警告.
+ 同一个链接只按一种基准书写, 不要混用两种基准.
+ 从 `SKILL.md` 直接引用, 保持一层深度.
+ 避免参考文件再引用其他参考文件, 形成多层链.
+ 需要读取参考文件时, 在正文说明读取条件和用途.

示例 (`SKILL.md` 中的写法):

```markdown
需要完整字段表时读取 `references/spec.md`.
生成文件后运行 `scripts/validate_skill.py`.
```

## 资源目录职责

| 目录 | 放什么 | 加载或执行方式 | 约束 |
| --- | --- | --- | --- |
| `scripts/` | 确定, 可重复执行的代码 | 由执行者运行, 不进入上下文 | 自包含或明确声明依赖; 错误信息可操作; 处理边界情况 |
| `references/` | 按分支读取的文档, 规范, 模板说明 | 需要时读取 | 单个文件保持聚焦; 文件越小, 按需加载越省上下文 |
| `assets/` | 进入产物的静态资源 | 通常由脚本读取, 不直接进入上下文 | 模板, 图片, 数据文件; 路径由脚本或正文明确引用 |

脚本语言没有标准限制. 常见选择是 Python, Bash 和 JavaScript, 实际支持取决于客户端.

## 标准字段与厂商扩展

### 可移植的标准内容

+ frontmatter 的六个标准字段.
+ 目录名与 `name` 一致.
+ `SKILL.md` 加 `scripts/`, `references/`, `assets/` 的目录约定.
+ 相对 skill 根目录的一层文件引用.
+ Markdown 正文中的步骤和说明.

只依赖这些内容时, skill 可以在不同客户端之间迁移.

### 常见厂商扩展

下表只说明差异, 不构成推荐用法. 具体客户端行为以目标客户端当前文档为准 (下表信息截至 2026-10).

| 来源 | 机制 | 其他客户端的行为 |
| --- | --- | --- |
| Claude Code | 额外 frontmatter, 如 `disable-model-invocation`, `user-invocable`, `argument-hint`, `context`, `agent`, `hooks`, `model`, `disallowed-tools`, `shell` | 本地加载通常忽略不认识的字段, 因此不会得到相同的调用控制或执行行为; 但 claude.ai 上传, Skills API 和 `package_skill.py` 会拒绝标准外字段并报 `Unexpected key(s)`, 不能假设所有路径都忽略 |
| Claude Code | `${CLAUDE_SKILL_DIR}` 等变量替换, `` !`command` `` 动态上下文注入 | 不会替换或执行, 文本可能原样出现 |
| Codex 与 ChatGPT | 可选的 `agents/openai.yaml`, 包含界面元数据, 调用策略和工具依赖 | 忽略该文件, 界面和调用策略不生效 |
| Claude Code, Codex, Vercel | plugin 或插件目录, marketplace manifest | 安装和分发方式不同, 不属于 Agent Skills 标准 |
| 各客户端 | `allowed-tools` 的具体语法和权限语义 | 字段属于标准, 但支持程度和解释不同, 不能依赖统一的权限行为 |

使用厂商扩展时:

+ 核心流程必须只依赖标准内容.
+ 在正文中标注扩展适用的客户端.
+ 提供不使用该扩展时的替代步骤.
+ 不把厂商的工具名, 元数据文件或调用方式写成通用规则.
+ 不把"忽略"当作唯一行为: 部分上传或打包路径会直接拒绝未知字段, 使用前按目标分发路径验证.

## 校验脚本覆盖的检查

`scripts/validate_skill.py` 把标准的明确违规作为错误:

+ frontmatter 缺失或不可解析.
+ `name` 缺失, 不是字符串, 长度或字符集不合法, 或与目录名不一致.
+ `description` 缺失, 不是字符串, 为空或超长.
+ `license`, `compatibility`, `metadata`, `allowed-tools` 的类型, 长度或空格分隔格式不合法. `allowed-tools` 是空格分隔的字符串, 含逗号, 分号或空格以外的空白字符 (如制表符) 即报错.
+ 正文为空.
+ `SKILL.md` 或 `references/` 下的 Markdown 参考文件 (`*.md`) 中的本地链接目标不存在, 包括以 `/` 开头的绝对路径链接指向不存在的目标. 本地链接先按 skill 根目录解析, 未找到再按链接所在文件目录解析. 解析路径前先对目标做 HTML 实体解码和百分号解码: `&amp;` 按 `&` 处理, `%20` 按空格处理, `%25` 按 `%` 处理, 其他百分号转义同理. 因此文件名含空格时链接写 `%20`, 含 `%` 时写 `%25`. 链接检查覆盖 Markdown 链接与行内 HTML 属性, 跳过外部链接, 纯锚点, 行内代码, 围栏代码块, 缩进代码块和 HTML 注释中的内容. 块引用前缀会被去掉后再判断代码块, 因此块引用内的缩进代码和围栏代码同样跳过; `<pre>`, `<script>`, `<style>`, `<textarea>`, CommonMark type 6 块级标签以及单独成行的完整开标签或闭标签 (type 7) 组成的原始 HTML 块 (大小写不敏感) 内的链接也不检查, 块外的链接照常检查. 原始 HTML 块只在行首 (最多 3 个空格缩进, 块引用前缀之后) 的标签处开启, 行内出现的 `<pre>` 等不开启块. `<pre>`, `<script>`, `<style>`, `<textarea>` 块持续到对应闭标签, 行首起始标签与闭标签同行时只屏蔽两者之间的内容; type 6/7 块持续到下一个空行, 其中 type 7 要求完整的开标签或闭标签独占一行, 标签后只有空白. type 7 块不能打断段落: 只有文档开头, 空行之后, 或标题, 分隔线, 围栏, 列表项之后的行首完整标签才开启块. 代码块, HTML 注释和原始 HTML 块之外的行内 `<a href>` 与 `<img src>` 目标也按本地链接检查. CommonMark 自动链接 (如 `<https://example.com>`) 与片段锚点 (`#...`) 不自动检查, 需要人工核对: 脚本不判断外部 URL 是否可达, 也不校对标题锚点是否存在. 脚注标签 (`[^1]: ...`) 和紧跟普通正文行之后的 `[x]: ...` 不按引用定义处理. 参考文件链接扫描只覆盖 `references/` 下不在隐藏文件或目录, `__pycache__` 中的 `.md` 文件; `references/` 下的其他文本文件 (如 `references/a.txt`) 中的链接不自动检查, 需要人工核对.
+ 本地链接目标包含 NUL 或 Unicode Cc 类控制字符 (含 C0, DEL 与 C1). 这类目标不进入文件系统调用, 直接报错并给出转义后的目标.
+ 引用式链接定义不存在. 正文中 `[文本][标签]` 形式的引用式链接没有对应的 `[标签]: 目标` 定义时报错. 定义存在时其目标按上面的本地链接规则检查, 不重复报错. 与链接检查使用同一套脱敏文本, 代码块和原始 HTML 块内的 `[文本][标签]` 不计; 空标签的折叠引用 (`[文本][]`) 和快捷引用 (`[标签]`) 不做存在性检查, 需要人工核对. 定义标签内允许反斜杠转义 (如 `[a\]b]: 目标`), 只有未转义的 `]` 才闭合标签, 这是 CommonMark 标签语法的一部分. `[标签]:` 之后的目标可以写在同一行, 也可以写在下一行; 跨行目标缩进或不缩进都可以, 列表项形式 (`- [标签]:`) 的跨行定义与相邻的多个跨行定义也同样会被识别. 定义行必须处于块首: 文档开头, 空行之后, 或标题, 分隔线, 围栏, 已识别的引用定义等块级结构之后; 紧跟普通正文行 (或普通列表项行) 的 `[标签]: ...` 属于惰性续行, 不构成定义. 定义行最多允许 3 个空格缩进: 4 个及以上空格的缩进 (缩进代码) 或列表项内容中的缩进定义不会被登记为引用定义, 例如列表项之下 4 空格缩进的 `    [文档]: 目标` 属于列表项内容, 本验证器不会把它登记为引用定义. CommonMark 允许引用定义出现在列表项内容中, pandoc 和 markdown-it 都接受 `- item` 换行再接 4 空格缩进的 `[文档]: 目标` 这种写法 (随后的 `[x][文档]` 能解析为链接), 这是本验证器的已知限制: 校验器有意不追求完整 CommonMark 语义, 边界以回归测试锁定, 不为覆盖这种写法扩大实现. 遇到这种写法应人工改写: 把定义移到列表之外并顶格书写 `[文档]: 目标`, 或写成列表项与定义同行的 `- [文档]: 目标`, 或把定义放到文档或章节开头的块首位置; 未改写时正文中对应的 `[文本][标签]` 会直接报告 `引用式链接定义不存在`, 属于错误而不是警告, 人工核对无法消除. 块引用前缀会被去掉后再判断定义, 因此文档开头或空行之后的 `> [标签]: 目标` 也能识别. 但块引用形式的引用定义只在块首位置识别: 普通段落行之后不带空行的 `> [标签]: 目标` 是段落的惰性续行, 定义不成立, 标签不会登记, 正文中对应的 `[文本][标签]` 会直接报告 `引用式链接定义不存在`, 属于错误而不是警告, 人工核对无法消除. CommonMark 规范允许块引用打断段落, markdown-it 和 pandoc 的 commonmark 读取器都接受这种写法, 这是本验证器的已知限制: 校验器有意不追求完整 CommonMark 语义, 边界以回归测试锁定, 不为覆盖这种写法扩大实现. 遇到这种写法应人工改写: 在段落与块引用定义之间加一个空行, 去掉块引用前缀直接写 `[标签]: 目标`, 或把定义移到文档或章节开头. 列表项内的块引用定义 (`- > [标签]: 目标`) 同样不会被识别, 标签不会登记, 对应的引用同样报告 `引用式链接定义不存在`; 应改写为 `- [标签]: 目标` 或在列表外定义. 目标后可跟一个可选的 CommonMark 标题: `"标题"`, `'标题'` 或 `(标题)`; 标题可以和目标写在同一行, 也可以独占紧随目标的一行 (`[标签]: 目标` 这样的同行定义允许标题紧接在定义的下一行); 独占行缩进或不缩进都可以, 列表项形式定义 (`- [标签]: 目标`) 之后未缩进的标题行同样属于该定义; 该独占行会被当作定义的一部分消费, 因此紧随其后的定义仍被视为块首. 只有整行都是引号或括号包裹的标题才算; 标题内部允许反斜杠转义 (如 `"标\"题"` 或 `(标\)题)`), 被转义的引号或括号不视为闭合符. 标题必须在一行内闭合: 本验证器只识别单行标题, 不识别跨多行书写的标题 (如 `[标签]: 目标 "标` 换行 `题"`, 或 `[标签]:` 换行 `目标 "标` 换行 `题"`). CommonMark 允许引用定义的标题跨多行书写, pandoc 也接受这种写法, 这是本验证器的已知限制; 跨行标题使该定义无法识别, 标签不会登记, 正文中对应的 `[文本][标签]` 会直接报告 `引用式链接定义不存在`, 属于错误而不是警告, 人工核对无法消除. 遇到这种写法应改写为单行闭合的标题, 或把标题与目标写在同一行 (如 `[标签]: 目标 "标题"`). 普通段落行 (如 `Some text`) 不是标题, 不会被消费, 其后的 `[标签]:` 仍按惰性续行规则处理. `<...>` 形式的目标允许空格, 裸目标不含空白. 目标后未加引号或括号的额外文本 (如 `a.md 标题`) 不是标题, 这种续行不识别, 需要人工核对. 同一行目标后的剩余文本同样必须为空或合法标题; 否则该行不构成定义, 既不登记标签也不检查目标, 正文中对应的 `[文本][标签]` 会报告定义缺失, 需要人工核对或改写. 续行是块级标记时同样不视为目标. 块级标记包括 Setext 标题下划线 (`---`, `===`, `==`), ATX 标题 (`# 标题`, `## 标题` 等) 和分隔线 (`***`, `___`). 这里的 `---` 是 Setext 标题下划线而不是分隔线: 作为段落续行时, markdown-it 和 pandoc 都把它判为 h2 下划线; `***` 和 `___` 没有 Setext 形式, 才是分隔线. 因此 `[标签]:` 之后紧跟 `---`, `===`, `==` 或 `# 标题` 时, 这些行属于块级标记, 不会当作未缩进目标; 定义不成立, 标签不会登记, 正文中对应的 `[文本][标签]` 会直接报告 `引用式链接定义不存在`, 属于错误而不是警告, 人工核对无法消除. 不同实现对这些行的归类存在分歧: markdown-it 和 pandoc 都把 `---` 判为 Setext 标题下划线; 对 `===`/`==`, pandoc 判为 Setext 标题下划线, markdown-it 可能当作有效目标; pandoc 还会把 `# 标题` 当作目标. 本验证器只对 `===`/`==` 沿用 pandoc 的 Setext 判断, 对 `---`, `===`, `==` 和 `# 标题` 一律按块级标记拒绝, 并不声称 `---` 和 `# 标题` 与 pandoc 语义一致. 遇到这种写法应人工改写, 把目标写在同一行 (如 `[标签]: 目标`), 或为跨行目标使用带引号的标题 (如 `[标签]: 目标 "标题"`) 明确边界, 避免依赖实现差异.
