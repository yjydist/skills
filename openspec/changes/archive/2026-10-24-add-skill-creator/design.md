# Design

## Context

见 `proposal.md` 的 Why. 与实现相关的现状:

+ 仓库现有 skill 的正文为 31 到 100 行, 细节放在 `references/`, 只有 `weekly-report` 带 `scripts/` 和独立测试. 新 skill 的体量应与现有入口一致, 不能把外部实现的全部章节搬进来.
+ 仓库没有 CI 和统一运行环境, 校验只能靠脚本本地运行或人工清单. `tests/` 使用 pytest, 通过 `.venv` 运行.
+ 三份外部实现的共同内核是目录结构, 渐进披露, 描述触发和自由度; 评测基建, 打包格式与 UI 元数据分别绑定 Claude Code, Anthropic 分发方式和 Codex.
+ Agent Skills 标准只约束 frontmatter 和"目录内含 SKILL.md", 正文格式和脚本语言由客户端自行支持.

## Goals / Non-Goals

**Goals:**

+ 产出的 skill 只依赖标准字段和标准目录约定, 换客户端后行为不变.
+ 硬约束只有一个来源: 正文不复述规则, 由 `references/spec.md` 和校验脚本共同承担.
+ 校验脚本可独立运行, 不要求安装第三方包, 误报可控.
+ 验证方法能在没有子 agent 和浏览器的环境中降级, 且降级本身是明确说明的.

**Non-Goals:**

+ 不实现测试运行器, 基准聚合, 审阅界面或描述自动优化循环.
+ 不定义 skill 的打包, 签名, 分发或安装格式.
+ 不生成宿主工具的 UI 元数据文件.
+ 不代替用户判断 skill 的业务价值, 只判断它是否值得做成 skill.

## Decisions

### D1: 两个参考文件按"能否通过"和"是否好用"切分

`references/spec.md` 承载可判定的约束: 目录结构, 字段表, 命名规则, 资源目录职责, 标准字段与厂商扩展的对照. `references/writing.md` 承载需要判断的方法: 描述公式与竞争测试, 触发语料构成, 正文模式, 自由度分配, 失败清单.

替代方案:

+ 单一参考: 两类内容混在一起, 创建时和校验时需要读同一份长文档.
+ 三个参考 (再加验证方法): 正文会多一次跳转, 而验证方法的篇幅不足以独立成篇.

两者都从 `SKILL.md` 直接引用, 不互相引用, 满足只引用一层的要求.

### D2: 硬约束只写在参考和脚本里

正文只写"属性, 原因和去向", 不复制名称正则, 字段长度或目录表. 原因是这些值会随标准修订变化, 复制到正文后必然与脚本漂移; 脚本报错时能指出具体规则, 正文只需要说明如何处理.

`init_skill.py` 与 `validate_skill.py` 各自保留名称规则, 不共用转换函数: 前者要把用户输入归一化为可创建的名称, 后者要保留输入原值并按标准报告违规, 两者的归一化语义不同. 规则一致性由 `tests/test_skill_creator.py` 的 `test_name_rules_match_between_init_and_validator` 保证, 该测试要求两个脚本对同一批输入的接受与拒绝结果一致, 任何一侧单独改规则都会让它失败.

替代方案: 正文保留一张速查表. 对高频约束更方便, 但会产生第二个来源, 且正文越长, 每次激活的成本越高.

### D3: 校验按错误和警告分级, 默认只对标准违规失败

错误为标准的明确违规: frontmatter 不可解析, name 缺失或不合法或与目录不一致, description 缺失或超长, 可选字段类型或长度错误, 正文为空, 本地链接目标不存在, 本地链接目标含 NUL 或控制字符, 引用式链接定义不存在. 警告分两组. 内容警告四类: 非标准字段, `scripts/` 或 `references/` 中未被 `SKILL.md` 直接引用或正文提到的文件, 参考文件以 Markdown 或行内 HTML 链接形式互相引用, 正文超过 500 行. 链接可移植性警告五类: 绝对路径链接 (目标存在时), Windows 盘符或 UNC 路径的链接, 链接目标在 skill 目录外, 链接路径大小写与磁盘不一致 (精确路径不存在但按大小写折叠能命中时, 目标仍视为已引用), 参考文件中的链接只能按所在文件目录解析. 这些警告默认只报告, 不使校验失败; `--strict` 时一律按错误处理. 也就是说, spec 里的 MUST 按这套分层执行: 默认只对标准违规失败, 严格模式才失败于可移植性风险, 默认不阻断合法但可移植性差的 skill.

未引用扫描只覆盖 `scripts/` 和 `references/`: `assets/` 可能由脚本在运行时拼接路径, 顶层文件(如 `LICENSE`)属于随 skill 分发的材料. frontmatter `license` 整体指向 skill 目录内现有文件时, 该文件视为已引用, 避免合法的许可证文件在严格模式下被判失败.

理由是误杀合法 skill 的代价高于漏报: 一个合法的 skill 被脚本判失败, 使用者会直接绕过整个校验. 反过来, 非标准字段和多余文件只是可移植性风险, 应该在交付说明中出现, 而不是阻断.

链接检查先按 CommonMark 常见结构脱敏, 再判定链接: 跳过围栏与缩进代码, 块引用前缀, 代码跨度, HTML 注释, 原始 HTML 块和引用定义等内容, 避免把示例代码或 HTML 模板误报为断链. 不引入第三方 Markdown 库, 边界由 `tests/test_skill_creator.py` 的回归测试锁定; 不为追求完整 CommonMark 语义扩大实现.

替代方案: 全部作为错误. 规则简单, 但会把带厂商扩展的合法 skill 拒之门外.

### D4: frontmatter 解析优先 PyYAML, 回退到内置受限解析器

脚本先尝试导入 PyYAML; 不可用时使用内置解析器, 支持单行普通标量, 单双引号标量和键, 块标量 (`|`, `>`), 一层嵌套映射和行内注释, 键与冒号之间允许空格. 不支持多行普通标量, 行内集合, 多行引号标量, 制表符分隔, 以 `- ` 或 `? ` 开头的纯量, 流指示符纯量, 以 YAML 指示符开头的纯量等结构; 完整支持/不支持清单以 `references/spec.md` 的内置解析器段落为准. 遇到这些结构时报错并提示安装 PyYAML 或人工确认. 两条路径共用同一套字段校验.

替代方案:

+ 强制依赖 PyYAML: 增加安装步骤, 与"脚本可选用"的定位冲突.
+ 纯正则逐字段提取: 对块标量和引号转义不可靠, 错误会表现为"字段不合法", 误导使用者.

内置解析器对无法识别的结构报"无法解析, 请人工确认", 不猜测语义.

### D5: 脚手架生成空 description, 不生成章节模板

`init_skill.py` 只创建目录, 合法的 frontmatter 和一句可删除的 TODO 注释, 提示填写 description, 写正文并删除本行. description 留空, 使校验必然失败, 迫使填写; 正文不预置章节, 避免执行者按模板填空而不思考结构.

替代方案:

+ 生成完整章节骨架和 TODO: 骨架一旦存在就很少被删, 容易留下与 skill 无关的段落.
+ 生成占位 description: 占位文本能通过长度校验, 等于没有强制.

脚手架拒绝覆盖已存在的目录, 名称不合法时不创建任何文件.

### D6: 验证按环境能力降级, 不把任一机制写成前提

三层: 机械校验总是执行; 触发语料由执行者判断或交给独立会话; 基线对照只在能启动独立会话时进行. 每一层都要求区分"已自动验证"和"人工核对", 未执行的层在交付说明中列出.

替代方案: 要求子 agent 或命令行 harness. 这与跨工具目标直接冲突, 在多数客户端里无法执行.

### D7: 仓库约定以钩子形式处理

正文要求"所在仓库对 skill 目录有额外规范时按规范补充", 不写死本仓库的 `docs/<name>.md` 和 README 条目. 这样 skill 可以原样复制到其他仓库, 本仓库的规范由 AGENTS.md 约束维护者.

替代方案: 内置本仓库约定. 对本仓库更省事, 但会让 skill 在其他仓库产生错误的文件和引用.

### D8: 不交付打包格式和评测基建

标准没有定义分发格式, 各工具安装方式不同; 评测基建依赖特定宿主. 两者都不进入首版. 正文只在需要时提示按目标工具文档处理.

### D9: 正文按九段组织

`SKILL.md` 正文固定为九个流程段: 适用与门槛, 意图收集, 内容去向, 描述与触发, 正文与自由度, 脚手架与校验, 验证, 改进现有 skill, 交付说明. 操作边界作为仓库惯例附在末尾. 九段只写判断, 理由和内容去向, 硬约束仍由 `references/` 和脚本承担.

## Risks / Trade-offs

+ 内置解析器与完整 YAML 语义存在差距 → 只接受常见写法, 无法识别时报错并提示安装 PyYAML 或人工确认; 测试覆盖引号标量和键, 键值间空格, 块标量, 注释, CRLF 和 BOM; 支持项对比 PyYAML 与内置解析器, 不支持项验证内置解析器报错并提示人工确认.
+ 校验警告过多会降低可信度 → 内容警告只保留四类, 另有五类链接可移植性警告; 不检查主观质量, 不判断描述写得好不好.
+ 触发语料的人工判断带有主观性 → 要求同时给出正例和近似负例, 并记录判断依据; 能启动独立会话时优先自动判断.
+ 正文与参考可能重复或遗漏 → 正文只写去向和原因, 硬约束集中在 `spec.md`; 审查时检查正文是否出现具体正则或长度值.
+ skill 自身随迭代膨胀 → 校验对正文超过 500 行给提示; 改进流程要求先删后加.
+ 门槛判断可能误拒 → 门槛只覆盖明显不适合的情况, 用户坚持创建时说明代价后继续, 不代替用户决策.

## Migration Plan

新增 skill, 不涉及现有文件的行为变更. 落地顺序:

1. 先写 `references/spec.md` 与 `references/writing.md`, 确定约束和方法.
2. 再写两个脚本, 使正文引用到的检查项真实存在.
3. 写 `SKILL.md`, 只保留决策和流程, 引用上述文件.
4. 补 `docs/skill-creator.md`, README 条目和测试.
5. 用一个临时样例 skill 走完整流程, 记录脚手架, 校验和降级路径的结果.

回滚方式为删除 `skills/skill-creator/`, `docs/skill-creator.md`, `tests/test_skill_creator.py` 和 README 条目, 不影响其他 skill.

## Open Questions

+ `writing.md` 是否需要中英双语示例. 当前按仓库规范只写中文, 若对外发布再补.
+ 校验是否要检查 `assets/` 和顶层文件中未被引用的文件. 首版只覆盖 `scripts/` 和 `references/`, 不检查 `assets/` 与顶层文件, 资产可能被脚本按运行时拼接的路径使用, 顶层文件(如 `LICENSE`)属于随 skill 分发的材料, 静态检查容易误报.
+ 是否附带一个最小示例 skill. 首版不附带, 避免示例被当作模板复制; 若实际使用中反复需要对照, 再补一个精简样例.
