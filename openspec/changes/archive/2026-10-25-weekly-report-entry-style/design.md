# Design

## Context

`weekly-report` 是"输入-渲染"型 skill: 执行模型收集内容并整理成 JSON, `scripts/render.py` 只做校验, 转义, 编译与产物发布, 不做任何措辞处理. 表述层原本没有任何落点, 只在 `SKILL.md` 里被"原样保留, 不改写"整体盖住.

仓库内已有三处示例互相不一致: 两个模板的数据块用名词化加句号 (`实验室主机的硬件设备的查看和对比。`), `SKILL.md` 的 JSON 示例用动宾无句号 (`查看和对比实验室主机的硬件设备`), 两处都用全角逗号.

两个模板还含 `#let period = "本周"` / `"本月"`, 作为考勤与自我评价三行的前缀. 那是版式文本, 与条目不共享同一条通路.

需求拆分的结论见 `proposal.md`, 条目与事实的具体约束见 `specs/weekly-report/spec.md`.

## Goals / Non-Goals

**Goals:**

+ 让条目有可辨认的目标口吻, 同时不让事实被改动.
+ 规则只以自然语言写在 `SKILL.md` 中, 由执行模型判断, 保持软性.
+ 仓库内所有示例 (模板数据块, `SKILL.md` JSON, 使用文档) 表达同一口吻.

**Non-Goals:**

+ 不改 `scripts/render.py` 的校验, 转义, 编译与发布逻辑, 不新增表述检查导致的失败退出.
+ 不引入正则或词表去机械删词.
+ 不改模板版式, 列宽, 字体与页面尺寸, 不改 `#let period` 前缀 (需求方已说明本 change 针对条目内容, 不是改模板).
+ 不改输入 JSON 字段与 CLI 参数.

## Decisions

### 1. 表述规则写在 `SKILL.md` 的自然语言里, 不进脚本

理由是表述属于判断题: 同一件事有多种合规写法, 取舍取决于事实与可读性. 正则只能删词, 不能把 `花了两天才跑通接口` 收敛成 `推进实验平台接口开发`, 也无法判断 `七八成` 该留.

替代方案: 在 `render.py` 中对 `我`, `本周`, `本月` 做替换并报错. 否决, 因为删除主语会产出 `完成了设备对比` 这类别扭句子, 且硬失败会挡掉合理条目.

### 2. 契约拆成两条需求, 而不是在"原样保留"里加例外

单条需求同时说"原样"和"按汇报口径改写", 模型只能自己猜边界, 表现为同一输入在不同轮次口吻不同.

替代方案: 在原需求后加一句"除第一人称与周期词外". 否决, 例外清单会继续膨胀到过程描述, 自我修饰, 名词化, 最终无法核对.

### 3. 用"风格说明 + 正反对照", 不用逐条硬规则

符合软性要求. 代价是一致性依赖模型判断, 因此 `SKILL.md` 需要给出足够密度的对照示例作为锚点, 交付核对再加一条"条目不含第一人称与周期词".

### 4. 四项短字段同一口吻, 但不强制动词开头

`实验室其他服务性工作`, `运动情况`, `心得体会`, `反思教训` 常是名词短语或 `无`. `日常锻炼` 改写成 `进行日常锻炼` 只为满足形式, 可读性变差.

### 5. 已成型的条目不重复改写

用户自己写好的条目若已是事项式陈述, 保持原样. 这条防止规则退化为"为改而改".

### 6. 示例统一为动宾, 无句号, ASCII 逗号

与选定口吻一致, 同时满足根 `AGENTS.md` 的标点要求. 模板数据块中的示例只在源码里作示范, 运行时会整体替换, 改动不影响渲染结果.

## Risks / Trade-offs

+ 软规则下同一输入多轮生成口吻可能不同 → 在 `SKILL.md` 提供 4 组正反对照, 交付核对增加一条表述检查.
+ 模型过度改写, 丢掉数字或过程性事实 → `事实原样保留` 保持硬约束, 核对时比对数字, 人名与条目数量.
+ 报告仍保留模板的 `本周` / `本月` 前缀, 与"条目无周期词"并存时观感不一致 → 记为非目标, 见 Open Questions.
+ 改动模板数据块示例可能触动 `tests/test_weekly_report.py` 中对源文件文本的断言 → 断言只覆盖 `name`, `student_id`, `次周报` 等, apply 时跑一次测试确认.
